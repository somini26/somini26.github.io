**위성 시스템 인증 에이전트**는 정답 문자열을 직접 비교하는 리버싱 문제가 아니었다. 입력값을 잘못 넣으면 검증 문구가 뜨는 대신, 복호화된 명령어가 정상적으로 실행되지 않았다.

그래서 비교할 정답을 찾는 방식보다 **입력값이 코드를 어떻게 바꾸는지** 확인하는 쪽으로 접근했다. 18개의 보호 단계를 역으로 분석해 인증값을 복원한 과정을 남겨둔다.

---

## 문제 개요

제공된 프로그램을 정상적으로 실행하고, 내부에 숨겨진 FLAG를 획득하는 리버싱 문제이다.

프로그램을 실행하면 사용자에게 인증값을 입력받지만, 일반적인 값을 입력할 경우 보호된 코드가 정상적으로 실행되지 않는다. 따라서 실행 파일 내부의 입력 검증 과정과 코드 복호화 구조를 분석하여 올바른 인증값을 복원해야 한다.

플래그 형식은 다음과 같다.

```text
flag{...}
```

---

## 파일 분석

압축파일을 해제한 결과 Windows 환경에서 실행되는 PE 형식의 실행 파일을 확인할 수 있었다.

프로그램을 실행하면 인증값을 입력할 수 있는 `Safe Executor` 형태의 입력창이 나타난다. 임의의 값을 입력하면 프로그램이 정상적으로 진행되지 않으므로, 입력값이 단순 문자열 비교가 아니라 내부 코드 복호화에 사용된다고 판단하였다.

실행 파일 내부 문자열과 함수 호출 구조를 분석한 결과 다음과 같은 특징을 확인하였다.

* 사용자 입력값을 받아 별도의 버퍼에 저장한다.
* 실행할 코드 일부가 암호화된 상태로 존재한다.
* 입력값을 이용하여 암호화된 코드 조각을 복호화한다.
* 복호화된 데이터가 올바른 명령어일 때만 다음 단계가 실행된다.
* 잘못된 입력값을 사용하면 유효하지 않은 opcode가 생성되어 실행이 중단된다.

즉, 프로그램은 정답을 직접 문자열로 비교하는 것이 아니라, 올바른 입력값을 사용했을 때만 보호된 코드가 정상적으로 복원되는 구조였다.

---

## 보호 코드 구조 분석

프로그램 내부에는 여러 개의 암호화된 코드 조각이 존재하였다.

각 코드 조각은 사용자 입력값의 일부를 이용하여 복호화되며, 복호화된 첫 바이트가 정상적인 기계어 opcode인지 검사한다. 올바른 값이 입력되면 해당 코드가 실행되고 다음 잠금 단계로 넘어간다.

전체적으로 약 18개의 잠금 단계가 연결된 형태였으며, 각 단계는 이전 단계에서 계산된 값과 사용자 입력값의 특정 위치를 함께 사용하였다.

구조를 단순화하면 다음과 같다.

```c
input = get_user_input();

for (stage = 0; stage < 18; stage++) {
    decrypt_code(stage, input);

    if (!is_valid_opcode(decrypted_code)) {
        exit();
    }

    execute_decrypted_code();
}
```

따라서 모든 입력값을 무작위로 대입하는 방식보다는, 각 단계에서 정상 opcode가 만들어지는 조건을 역산하는 것이 효율적이다.

---

## 인증값 복원

각 단계의 암호화된 바이트와 복호화 연산을 추적하였다.

보호 코드의 첫 명령어는 실행 가능한 opcode여야 하므로, 복호화 결과가 정상적인 명령어가 되는 입력 바이트를 역으로 계산할 수 있었다.

예를 들어 암호화된 코드가 다음과 같은 연산으로 복호화된다고 가정할 수 있다.

```c
decrypted_byte = encrypted_byte ^ input[index] ^ key;
```

정상 opcode 값을 알고 있다면 입력값은 다음과 같이 역산할 수 있다.

```c
input[index] = encrypted_byte ^ key ^ expected_opcode;
```

이러한 방식으로 각 잠금 단계에서 사용되는 입력 위치와 연산값을 분석하였다.

한 단계에서 복원된 값은 다음 단계의 키 계산에도 사용되기 때문에, 첫 단계부터 순서대로 조건을 해결하였다. 총 18단계의 잠금 조건을 모두 분석한 결과 프로그램이 요구하는 54바이트의 인증값을 복원할 수 있었다.

복원된 인증값은 다음과 같다.

```text
flag{DbLYd5WTNB3HrUoB6Uu2JBmw5ktQnLQijzQfkt4rdtat663n}
```

---

## 실행 검증

복원한 값을 프로그램의 입력창에 그대로 입력하였다.

```text
flag{DbLYd5WTNB3HrUoB6Uu2JBmw5ktQnLQijzQfkt4rdtat663n}
```

입력 후 모든 보호 코드가 정상적으로 복호화되었으며, 프로그램에서 다음과 같은 성공 메시지가 출력되었다.

```text
Protected Program has been executed successfully.
```

이를 통해 복원한 입력값이 실제 프로그램의 모든 인증 단계를 통과하는 올바른 FLAG임을 확인하였다.

## 결론

이 문제는 입력값을 일반적인 비교 함수로 확인하는 것이 아니라, 입력값을 암호화된 코드의 복호화 키로 사용하는 방식이었다.

잘못된 값을 입력하면 보호 코드가 올바른 기계어 명령어로 복호화되지 않기 때문에 프로그램이 정상적으로 실행되지 않는다. 반대로 각 단계에서 요구하는 opcode 조건을 역산하면 입력값을 한 부분씩 복원할 수 있다.

최종적으로 18개의 잠금 단계를 모두 분석하여 54바이트의 인증값을 복원하였으며, 실제 프로그램에서 정상 실행 성공 메시지가 출력되는 것을 확인하였다.

## 풀고 나서

일반적인 문자열 비교가 보이지 않아도 프로그램에는 통과 조건이 있다. 이 문제에서는 그 조건이 **실행 가능한 기계어를 만드는 입력값**이었다.

입력 검증과 코드 복호화가 연결되어 있다는 걸 확인한 뒤에는 각 단계를 나눠 역산하는 방식으로 풀 수 있었다. 다음에는 유사한 보호 코드를 만나도 흐름부터 차근차근 그려봐야겠다.
