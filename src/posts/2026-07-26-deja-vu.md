## SecureVault Logging API — AES-GCM Nonce Reuse

### 1. 문제 개요

로그 서비스는 모든 로그 항목을 AES-256-GCM으로 암호화합니다.

관리자가 플래그를 포함한 비밀 로그를 저장해 두었으며, 다음 API를 통해 암호화된 데이터를 확인하거나 새로운 로그를 저장할 수 있습니다.

```text
GET  /flag_entry
POST /log
```

`/flag_entry`는 관리자 로그의 nonce, ciphertext, tag를 반환하고, `/log`는 사용자가 입력한 메시지를 로그 형식으로 저장한 뒤 암호화 결과를 반환합니다.

목표는 암호화된 관리자 로그에서 플래그를 복구하는 것입니다.

### 3. 취약점 분석

AES-GCM은 동일한 키와 nonce 조합을 두 번 이상 사용하면 안 됩니다.

AES-GCM의 암호문은 단순화하면 다음과 같이 생성됩니다.

```text
C = P XOR KS
```

* `C`: 암호문
* `P`: 평문
* `KS`: 키와 nonce로 생성되는 키스트림

동일한 키와 nonce를 사용하면 동일한 키스트림이 생성됩니다.

따라서 관리자 암호문과 사용자가 만든 암호문이 같은 nonce를 사용한다면 다음 관계가 성립합니다.

```text
C_admin = P_admin XOR KS
C_user  = P_user  XOR KS
```

두 식을 XOR하면 키스트림이 제거됩니다.

```text
C_admin XOR C_user
= P_admin XOR P_user
```

사용자 평문 `P_user`는 직접 선택할 수 있으므로 관리자 평문은 다음 식으로 복구할 수 있습니다.

```text
P_admin
= C_admin XOR C_user XOR P_user
```

즉, `/log` 요청을 반복해서 관리자 로그와 동일한 nonce가 나오도록 만들면 됩니다.

### 4. 선택 평문 암호화

Burp Suite의 Repeater에서 다음 요청을 전송했습니다.

```http
POST /log HTTP/1.1
Host: 15.164.79.100:11014
Content-Type: application/json
Connection: close

{"message":"AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"}
```

서버는 입력한 문자열만 암호화하는 것이 아니라 다음과 같은 JSON 구조로 저장합니다.

```json
{"user":"guest","role":"user","note":"AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"}
```

따라서 이 JSON 전체가 우리가 알고 있는 선택 평문이 됩니다.

처음 요청에서는 다음과 같이 관리자 로그와 다른 nonce가 반환됐습니다.

```text

```

다시 요청했을 때는 다음 nonce가 반환됐습니다.

```text

```

같은 요청을 반복해서 전송한 결과, 관리자 로그와 동일한 nonce를 사용하는 응답을 얻었습니다.

### 5. 평문 복구

다음 Python 코드를 사용해 관리자 로그를 복구했습니다.

```python
admin_ciphertext = bytes.fromhex(
    "631033e28727a90f484abaab4c25bd3df62350340c5d3005b918098299866091"
    "ed0d9b78667c711a058c904e68b0410064bd91c2870a5ce7e0a7c0cd620537"
    "f0bfe5640d79faf6b723d6de65de99b4498fcb46ed691307bdac"
)

user_ciphertext = bytes.fromhex(
    "631033e28727a90f484caba3563fbd3df62350340c5d3005be04038499866091"
    "ed0d9b78667c730f02b6a57819ae747048998ff3f22f42d5d594b0e746372985"
    "9990142267d5879801f2c056faed856dadfe58dc44213bde90196a122a320d198"
    "854ea91b6a61e1ef01dea0304ce75ae69b5"
)

known_plaintext = (
    b'{"user":"guest","role":"user","note":"'
    + b"A" * 74
    + b'"}'
)

admin_plaintext = bytes(
    admin_byte ^ user_byte ^ plain_byte
    for admin_byte, user_byte, plain_byte
    in zip(admin_ciphertext, user_ciphertext, known_plaintext)
)

print(admin_plaintext.decode())
```

### 7. 결론

이 문제의 핵심 취약점은 AES-256-GCM에서 nonce 후보 공간을 지나치게 작게 설정해 nonce 충돌이 발생한 것입니다.

AES-GCM 자체는 안전한 인증 암호화 알고리즘이지만, 동일한 키와 nonce 조합을 재사용하면 같은 키스트림이 생성됩니다. 공격자는 자신이 알고 있는 평문과 그 암호문을 이용해 동일한 nonce로 암호화된 다른 평문을 XOR 연산만으로 복구할 수 있습니다.

이를 방지하려면 같은 암호화 키를 사용하는 동안 nonce가 절대로 중복되지 않도록 해야 합니다. 일반적으로 96비트 무작위 nonce를 충분한 난수 생성기로 생성하거나, 중복되지 않는 카운터 방식으로 관리해야 합니다.
